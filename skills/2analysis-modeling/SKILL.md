# 赛题分析与建模设计

## 数学建模规范参考

如需领域判断，读取 `../_references/math_modeling_norms.md` 中的“赛题理解与子问题识别”“假设与模型建立”和“题型防错速查”小节。该文件只作为规范知识库，不替代本阶段的分析报告结构。

## 必须产出

在当前工作目录的 `reports/` 子目录中创建或更新：

- `reports/ANALYSIS_MODELING_REPORT.md`：
  - 赛题分析、子问题拆解、数据与附件理解、评价标准、关键歧义和假设预检。
  - 变量、符号、模型假设、目标函数、约束条件、求解算法、各子问题实现口径、代码阶段任务清单

不要在本阶段写论文正文，不要生成最终 `paper/`，不要把图表排版任务提前到这里。


## 工作流程


### Step 1: 子问题拆解

只把题面中明确编号的顶层问题当作子问题，例如“问题一/二/三”“Problem 1/2/3”。不要把小问、背景描述、数据说明、提交要求误当成独立子问题。

在 `ANALYSIS_MODELING_REPORT.md` 开头明确写：

根据题目动态调整问题数量

本赛题共 X 个子问题。

每个子问题要说明：

- 输入数据和已知条件。
- 决策变量或预测对象。
- 目标函数或评价指标。
- 约束条件。
- 与其它子问题的依赖关系。
- 绘制哪些图像或表格来展示结果。

### Step 2: 假设敏感性预检

列出关键歧义，不要急着定模型。对影响结果的歧义至少给出两种解释，并用简单验算或逻辑递进判断选择。

必须在 `ANALYSIS_MODELING_REPORT.md` 中包含：

```markdown
## 假设敏感性预检

### 模糊表述及解释
...

### 快速验算与递进性检查
...

### 最终采用的解释
...

### 绘制的图像和对比表格


```

如果某个假设会让后续问题的新增条件没有边际效果，要回头调整解释.

### Step 3: 数据理解与建模路线

对每份附件做数据理解：

- 行列规模和字段解释。
- 缺失、异常、重复、单位不一致。
- 可直接用于建模的变量。
- 需要派生的指标。

然后给出总体路线：

```text
题面 -> 数据清洗(EDA) -> 子问题一模型 -> 子问题二模型 -> 。。。。 -> 结果检验 -> 论文展示
```

### Step 4: 建模报告

在 `ANALYSIS_MODELING_REPORT.md` 中写出可交给代码阶段实现的完整方案。

每个子问题必须先讲清楚思路，再展开数学模型和实现算法。读者在看到公式前，应先明白“为什么这样建模、数据怎样流动、该模型解决什么困难”；代码阶段在读完算法后，应能直接拆成函数和任务，不需要自行补齐关键口径。

#### 每个子问题的展开顺序

按下列逻辑组织内容，标题可按题目语义调整，但不得省略适用项：

1. **问题目标与总体思路**
   - 用一段连贯文字说明输入、待求对象、核心困难、选用的模型族及选择理由。
   - 给出从原始数据到最终结论的步骤链，例如“构造分析单元 → 定义变量 → 建模 → 求解 → 检验 → 形成结论”。
   - 说明本问与前后子问题的继承关系，以及相比基准方法新增了什么能力。
2. **分析单元、变量与数据处理**
   - 明确观测层级、索引、聚合键、排序键、单位、有效样本口径和缺失/重复处理。
   - 定义因变量、自变量、决策变量、派生变量及必要的变换、标准化或边界修正公式。
   - 涉及重复测量、时间序列、空间层级或分组数据时，明确最小独立单位，避免伪重复和数据泄漏。
3. **模型建立与选择理由**
   - 从题目机制或数据特征推导模型，而不是只报模型名称。
   - 写出完整模型公式、目标函数、约束、参数含义、随机项或误差分布，以及参数可行域。
   - 设置至少一个合理基准或替代模型，并说明采用统一样本、统一尺度和统一评价口径的比较办法。
   - 若模型有非线性、交互、删失、异质性、多目标或鲁棒项，逐项解释其作用及不加入时的后果。
4. **详细求解算法**
   - 先把公式落到可计算对象：数据矩阵、状态、候选集合、损失函数或递推量。
   - 给出编号算法步骤，包括初始化、每轮计算/更新、约束处理、模型或超参数选择、终止条件和最终输出。
   - 指明关键实现口径：训练/验证划分单位、随机种子、参数范围、网格粒度、优化器或求解器、数值容差、重采样单位与次数如何确定。
   - 对迭代算法写明收敛判据与最大迭代限制；对枚举、动态规划或搜索写明候选空间、状态转移/剪枝和复杂度；对闭式解写出计算式；对仿真写明抽样分布和重复流程。
   - 说明不可行、未收敛、奇异拟合、样本过少等失败情形的识别标准与降级方案。
5. **统计检验、评价与诊断**
   - 每个检验写明原假设、统计量或评价量、比较对象、数据尺度和判定口径。
   - 区分样本内拟合、交叉验证性能和外部泛化，避免混用；涉及调参时使用无泄漏的验证流程。
   - 给出残差、稳定性、敏感性、约束回代和基准对照等诊断，并说明异常结果如何影响模型选择。
6. **结果解释与结论形成**
   - 规定结果应按什么逻辑解释，哪些参数、区间、图表或对比支撑每条结论。
   - 不预写尚未计算的数值结论；使用“待由模型输出填入”的可追溯结果项。
7. **输入输出与代码接口**
   - 列出最小输入字段、处理中间表、模型产物、评价表、图片及最终结论所需字段。
   - 固定会影响复现的口径，并说明论文中的每个数值和图表如何追溯到导出表。

#### 算法具体性要求

“采用某模型”“调用某软件包求解”“进行交叉验证/Bootstrap/敏感性分析”不能单独算作算法。必须进一步回答：

- 数据具体如何进入模型，分析单元和索引是什么；
- 参数或决策变量具体如何估计、更新或搜索；
- 候选方案如何比较并选出最终方案；
- 何时停止，失败时如何处理；
- 输出哪些可供下一阶段直接读取的字段、表和诊断标记。

公式要清楚到能逐项映射为代码变量。算法细节应与问题难度匹配：简单闭式模型无需虚构迭代过程，复杂模型不能用一句“使用优化算法求解”带过。

推荐结构：

```markdown
# 建模报告

## 1. 总体建模框架
## 2. 数据处理方案
## 3. 符号说明
## 4. 问题一模型
## 5. 问题二模型
## 6. 问题三模型
    .... 
## 7. 灵敏度分析与检验方案
## 8. 代码实现任务清单
```

如果子问题数量不是 3 个，按实际题面调整章节，不要硬凑。

### Step 5: 给代码阶段的接口

在 `ANALYSIS_MODELING_REPORT.md` 末尾写一个“代码实现任务清单”，格式如下：

```markdown
## 代码实现任务清单

| 任务 | 输入 | 输出 | 方法 | 校验 |
| --- | --- | --- | --- | --- |
| 问题一 | ... | ... | ... | ... |
| 问题二 | ... | ... | ... | ... |
```


## 质量要求

- 所有结论都能回到题面或数据。
- 不编造数据字段和数值。
- 不跳过歧义分析。
- 模型既要有数学表达，也要能被代码实现。
- 若数据不足或题面不清，要明确记录风险和替代方案。
- 每个子问题开头先有不依赖公式也能读懂的思路说明，后续公式、算法、检验和输出均与该思路一一对应。
- 不把方法名当作方案；关键算法必须包含初始化或构造、计算步骤、选择规则、终止条件、失败处理和输出。
- 模型比较必须使用可比的数据、尺度和指标，并明确基准模型；不能默认复杂模型更优。
- 报告中的数学对象、算法步骤、代码任务清单和最终导出字段必须能够互相追溯。
