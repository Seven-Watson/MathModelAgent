# 编程实现与数据图表生成

本 skill 承接 `2analysis-modeling`。目标是把 `reports/ANALYSIS_MODELING_REPORT.md` 里的模型和算法落实为可复现程序，跑出可信结果，并生成论文中需要的数据型图表。

## 数学建模规范参考

如需领域判断，读取 `../_references/math_modeling_norms.md` 中的“题型防错速查”“代码实现与结果”“编码阶段常见错误”和“图表与可视化”小节。该文件只作为规范知识库，不新增本阶段的固定产物。

## 阶段边界

- 本阶段负责：代码、实验运行、结果、结果表、数据驱动图表。
- 本阶段不负责：技术路线图、算法流程图、系统架构图、概念示意图。这些交给 `4drawio`。
- 本阶段不写论文正文，只为 `5writing` 提供可信数值和图表资产。


### Step 1: 代码结构

按 `plan.md` 中"项目目录结构"创建 `code/` 和 `figures/` 骨架，再开始写代码。子问题数不一定是 3，按赛题实际数量调整。

代码按执行顺序使用两位数字前缀，例如 `01_data_preprocessing.py`、`02_model_fitting.py`。每一步生成的机器可读结果使用相同前缀，例如步骤 01 生成 `01_analysis_data.csv`。直接写最终编号文件，不同时保留无编号副本。


### Step 2: 逐子问题实现

按子问题顺序实现，不要一次性写完不跑。

每个子问题必须完成：

1. 读取所需数据。
2. 实现模型或算法。
3. 验证约束。
4. 输出核心结果。
5. 绘制丰富的图表。
6. 在 `reports/RESULTS_REPORT.md` 中写清楚方法、关键数值和校验结果。

优化类问题必须先保证可行解，再优化目标值。预测类问题必须做训练/验证划分或合理误差评估。评价类问题必须说明指标方向、归一化方法和权重来源。

### Step 3: 结果文件格式


AI 在实现、求解和作图过程中，必须把关键中间过程保存成数据并做好记录，例如清洗后的数据摘要、模型参数、迭代历史、约束检查、灵敏度分析过程、图表所用数据和运行日志。中间数据优先保存到 `figures/` 或 `code/outputs/`，并在 `reports/RESULTS_REPORT.md` 中说明文件用途。

`reports/RESULTS_REPORT.md` 推荐结构：

```markdown
# 计算结果

## 运行环境
## 数据读取与预处理
## 问题一结果
## 问题二结果
## 问题三结果
## 灵敏度分析
## 约束与一致性校验
## 与建模报告的一致性说明
## 可复现运行方式
```

所有数据和图表结果都必须出现在 `reports/RESULTS_REPORT.md` 中引用

命名约束：编号只用于步骤代码以及代码生成的 CSV、JSON、TXT 等机器可读结果。Markdown 报告使用本 skill 规定的标准名称，不添加步骤编号，也不生成编号副本。

### Step 4: 生成数据驱动图表

根据 `reports/ANALYSIS_MODELING_REPORT.md` 和 `reports/RESULTS_REPORT.md` 规划图表，生成 PDF 到 `figures/`。

#### 4.1 先规划结论与证据

- 每张图在编码前先写出它必须支持的一句话结论；不能支持明确结论的图不生成。
- 多张图表达同一结论时，优先合并为多面板图或删除次要图，避免只是更换横纵轴重复展示同一证据。
- 多面板图中的每个面板必须承担不同的证据角色，例如数据分布、主效应、模型比较、稳健性或诊断，而不是重复绘制同一结果。
- 图表服务于模型结论和证据完整性；复杂版式、模板匹配和视觉装饰不得优先于正确、清晰和可复现。

典型图表：

- 预测类：真实值-预测值对比、误差分布、指标对比。
- 优化类：收敛曲线、成本对比、资源利用率、方案前后对比。
- 评价类：综合得分排序、雷达图、热力图、敏感性曲线。
- 数据理解：分布图、趋势图、相关性图、箱线图。

图表要求：

- PDF 矢量输出，适合论文。
- 不在图内写大标题，标题交给论文 caption（Typst 的 `caption:` 或 LaTeX 的 `\caption{}`）。
- 中文论文图表使用中文坐标轴和图例；英文论文使用英文。
- 不生成流程图/架构图/路线图。
- `figures/` 下的图表文件不添加步骤编号，例如使用 `p1_ff_ga_effect.pdf`，不得同时生成 `04_p1_ff_ga_effect.pdf` 等编号副本。

#### 4.2 论文级视觉规范

- 默认使用白色背景、克制配色和跨面板一致的视觉语义。一个主色族表达核心结果，一个辅助色族表达分组；红色主要用于阈值、风险或强调，不作为普通类别色滥用。
- 主曲线、主要数据和关键结论应当最醒目。置信区间使用低透明度填充，且视觉显著性必须低于对应主曲线。
- 类别位置固定、文字不拥挤时优先直接标注；使用图例时不得遮挡数据、置信区间、误差线或统计标记。
- 中文标签、单位、缩写和模型名称必须准确。不得使用自动标题化或统一大小写转换破坏 `XGBoost`、`RF`、`LSTM` 等专有名称。
- 多面板图统一绘图区尺寸、可比较坐标范围、字体、线宽和面板标号位置。若科学含义要求不同坐标范围，必须在图表记录中说明理由。
- 在论文最终插入尺寸下检查可读性，所有文字和数学符号不得小于 5 pt。
- 正式交付至少包含 PDF；用户要求投稿级交付时，同时输出保留可编辑文字的 SVG 和 600 dpi TIFF。不同格式是同一张图的格式副本，不增加图表数量，也不加步骤编号。
- 每张正式图必须能追溯到 `code/outputs/` 中带步骤编号的 CSV 或 JSON 数据。不得只保存图片而不保存图表数据来源。
- 不得为了美观、降低密度或迁就模板而删除样本。确有科学或统计理由需要排除时，记录排除前后数量、精确规则和原因，并保留原始数据不变。
- 自动检查不能代替人工检查。每次修改数据几何、坐标、字体、图例、注释或布局后，都要在最终物理尺寸下逐面板检查文字、留白、遮挡、颜色层级、不确定性表达和歧义。

#### 4.3 GPT Image 视觉辅助

每张正式候选图由代码生成首版预览后，若当前环境提供内置 GPT Image，则默认调用一次生成视觉设计参考稿。该步骤只提供审美和版式建议，不得成为定量图的渲染来源。

允许 GPT Image 提出或展示的变化仅限：

- 配色与颜色层级；
- 留白与版面平衡；
- 字体层级与标签可读性；
- 图例位置；
- 线宽、点大小和透明度；
- 多面板比例；
- 三维图观察角度；
- 信息层级与视觉焦点。

必须拒绝任何会造成下列变化的生成结果或建议：

- 改变数据点位置、曲线形状或分布形状；
- 改变置信区间、误差线或不确定性范围；
- 改变坐标范围、单位、统计阈值或参考线；
- 新增显著性、数值、机制、因果关系或模型结论；
- 改变中文标签、缩写或符号的含义；
- 直接把生成式位图作为论文定量图。

固定工作流为：

```text
真实数据代码图
→ GPT Image 视觉参考稿
→ 提取可执行样式建议
→ 修改原绘图代码
→ 重新由代码生成正式图
→ 数值和视觉验收
```

正式图始终由可复现的 Python、R 或项目既定绘图代码基于真实数据重新生成。不得从 GPT Image 参考稿中描摹、读取或反推数据。GPT Image 不可用、调用失败或输出不可信时，记录原因并继续确定性绘图流程，不得阻断问题求解、结果报告或正式图交付。

#### 4.4 辅助文件与向后兼容

保持现有正式接口不变，只允许增加以下可选辅助文件：

- 正式图：`figures/p1_xxx.pdf`；
- 图表数据：`code/outputs/problem1/04_xxx_data.csv`；
- GPT Image 参考稿：`figures/design_references/p1_xxx_style_reference.png`；
- 设计记录：`code/outputs/problem1/04_figure_design_manifest.json`。

`04_figure_design_manifest.json` 至少记录图名、一句话结论、证据角色、图表数据路径、是否调用 GPT Image、采纳的样式建议、拒绝的生成式变化、失败或跳过原因以及最终验收状态。它属于机器可读结果，因此使用对应绘图步骤编号。

`figures/design_references/` 只保存视觉参考，必须明确标记“视觉参考，非数据图”，并满足以下隔离规则：

- 不写入正式图清单；
- 不被论文写作阶段自动引用；
- 不参与正式图数量统计；
- 不替代 PDF、SVG 或 TIFF 正式图。

这些辅助文件均为可选增量。旧项目没有 `design_references/` 或设计记录时仍然合法，不要求改名、迁移或重跑；原有代码编号、结果编号、目录结构、`RESULTS_REPORT.md` 和正式图接口继续有效。

图表可以由主程序或独立脚本生成，不强制固定脚本名。无论采用哪种方式，都必须保存图表对应的数据来源和生成记录。
